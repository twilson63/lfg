The thesis
01

The plan is not the conversation.

LFG’s defining move is architectural, not procedural: it pushes state out of fragile chat history and into inspectable artifacts. The parent agent owns execution. Planner and reviewer subagents are advisory critics. Tests, screenshots, diffs, and logs become evidence—not vibes.

The result is closer to a tiny project operating system than a prompt trick.

Finite-state workflow

Ten phases. One direction of travel.

Every phase narrows uncertainty. Research discovers reality. Definition removes ambiguity. Planning turns goals into observable contracts. Evaluation either advances or routes the step back through diagnosis and a fresh plan.

The engine

Replan. Don’t replay.

A failed criterion does not justify another identical attempt. LFG requires a diagnosis, an updated progress record, and a materially better plan—smaller step, different seam, or stronger evidence.

Interactive repair loop

Simulate a failing step

Each attempt must carry new information. The guide allows early escalation for a true blocker or after three distinct replans of one step yield no new approach.

Awaiting evidence…
A wording tension in v3: the loop is called “bounded,” but it says to continue for at least 15 repair/replan iterations across the task. A production adaptation should usually define both a minimum diligence threshold and a hard maximum budget.
Session durability

Leave breadcrumbs a new session can trust.

Checkpoints turn the process into a resumable state machine. On re-entry, the agent reads forward from the latest anchor instead of reconstructing intent from a compressed transcript.

task/begin

Slug, intent, initial scope, current branch.

task/plan-approved

Reviewed plan exists. Blocking questions are resolved.

task/step-N-done

Criterion status plus pointer to evidence.

task/complete

Validation, residual risks, durable decisions.

Security invariant: summarize checkpoints. Never copy secrets, private keys, prompts, credentials, or raw browser DOM into handoff or memory files.

LLM-as-judge

Green tests are necessary. Not sufficient.

The judge checks whether the implementation solved the planned problem, not merely whether a command exited zero. Design-sensitive work also gets a taste and originality score; below 4/5 triggers repair unless speed was explicitly preferred.

Critical reading

What is strong—and what needs tuning.

The strong ideas

  • Acceptance criteria before code make success observable.
  • Independent plan and implementation gates reduce self-review bias.
  • Artifacts as state make long tasks resumable and auditable.
  • Replanning on failure prevents expensive repetition.
  • Security-sensitive work never fast-paths is the right conservative default.

The sharp edges

  • “At least 15” attempts conflicts with the promise of a bounded loop; add a hard ceiling.
  • The source defaults show docs/-prd.html and docs/-progress.html; a task slug appears to be missing.
  • HTML is excellent for human dashboards, but structured JSON/YAML may be safer for machine state alongside it.
  • Checkpoint verbs are conceptual unless the host exposes a real checkpoint API.
  • Taste scoring is useful but subjective; record concrete reasons, not just numbers.
The important shift

The agent stops being a typist. It becomes an evidence operator.

LFG’s value is not more steps. It is a chain of explicit claims, each paired with proof, review, and a recovery path.
