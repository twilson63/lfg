LFG

Lets Fucking Go — a bounded research → plan → implement → review loop that actually ships.

Turn an agent from a code monkey into a disciplined engineer: research the codebase, plan with evidence, implement step by step, review with a judge, and repair failures with fresh plans — across session boundaries.

01

Most agent loops drift.

Vague goals, hidden state, no evidence a step passed. The agent writes code, runs tests, and calls it done — but the tests were never tied to the goal. When the session compacts, it replays the same mistakes from scratch.

P · 01
Coordination

Files, not chat history

An HTML PRD and an HTML progress doc are the single source of truth. The agent, subagents, and human all inspect the same artifacts. Chat history is never the plan.

P · 02
Discipline

Acceptance criteria per step

Every planned step ships with observable conditions and the evidence required to prove them — before any code is written.

P · 03
Persistence

Replan, don't just retry

On failure, diagnose and write a better plan. The loop runs at least 15 repair/replan iterations before escalating.

P · 04
Durability

Session checkpoints

Anchors at begin → plan-approved → step-N-done → complete survive compaction and re-entry.

03

Triage: full loop vs fast path.

Answer three questions before starting. If all say "Yes" → fast path. If any says "Maybe" or "No" → full loop. Security-sensitive boundaries never get the fast path.

Full Loop · default

The ceremony

Broad, ambiguous, design-sensitive, or security-sensitive work.

  • PRD HTML + progress HTML written first
  • Planner subagent produces the plan
  • Plan-review gate before any code
  • Per-step acceptance criteria + evidence
  • Implementation-review gate after the diff
  • Checkpoints at begin → plan-approved → step-N-done → complete
Fast Path · opt-in

Just ship it

Only when all three conditions are true.

  • Change touches ≤30 lines across ≤3 files
  • No security / IPC / approval / path / browser / UX / copy / architecture surface
  • An obvious validation command exists
  • Skip PRD/progress HTML, skip planner
  • Make the change, run validation, self-review against the goal
  • Checkpoint/memory handoff optional

04

Coordination lives in files.

An HTML PRD and an HTML progress doc are the single source of truth — readable by agent, subagents, and humans, opening directly in a browser.

docs/-prd.html
docs/-progress.html

      

      

        
Why HTML, not Markdown

        
Rendered HTML gives real structure — sections, tables, status chips, and links to changed files — and opens directly in a browser without a separate viewer. The PRD and progress docs double as a human-readable dashboard.

        
Markdown would collapse this to flat text. The HTML is self-contained: inline minimal CSS, no external scripts, no remote fetches, so it renders from file:// and stays safe to share.

        
Never rely on chat history for coordination. Copy subagent plans and reviews into the PRD or progress HTML explicitly.

      

    

  







  

    
05

    
Subagents are advisory critics.

    
Never unbounded autonomous owners. The parent stays in control; the planner proposes, the judges gate. Prefer fork context for reviewers so they judge a stable snapshot.


    

      

        
◎

        
Planner

        
read-only · fresh context · no edit

        
A skeptical product-minded architect, not a code generator. Produces a step-by-step plan with acceptance criteria and required evidence for every step.

Reviewer · Plan gate

        
read-only · fork · strict critic

        
Reviews the PRD HTML before implementation. Confirms definition of done, goal coverage, research completeness, and that every step has acceptance criteria.

read-only · fork · reads diffs + runs validation

        
Reviews the uncommitted diff against the PRD. Evaluates each step separately against its acceptance criteria with evidence.

06

    
The LLM-as-judge rubric.

    
Every change is scored across eight areas. Unmet required criteria are blockers; taste or originality below 4 triggers a repair loop for design-sensitive work.


    

      
Correctness
Does the change solve the stated problem without regressions?
required

      
Acceptance coverage
Does every planned criterion have evidence?
required

      
Security / privacy
Secrets, credentials, prompt contents, command output, approval-gated effects handled safely?
required

      
Simplicity
Cohesive, idiomatic, not over-engineered?
required

      
Taste
Polished, restrained, product-appropriate UX/API/copy/architecture?
1–5 · <4 = repair

      
Originality
Avoids generic cookie-cutter output while staying consistent with the project?
1–5 · <4 = repair

      
Maintainability
Will future contributors understand and extend it?
required

      
Validation
Were the right tests / checks / manual verifications run?
required

    

  







  

    
07

    
The workflow, step by step.

    
From context inspection to final report — each step leaves a checkpoint the next session can recover from.


    

      
Phase 01
Inspect context
Check branch + working tree. Preserve unrelated user changes. Read project instructions and relevant files. Record a task/begin checkpoint for the full loop.
checkpoint: begin

      
Phase 02
Define the concept first
Before writing code, define the core term in this project's language: what it means here, what it explicitly doesn't, privacy/security implications, measurable success criteria.

      
Phase 03
Write or update the plan
Invoke the planner subagent. Create PRD + progress HTML. Each step ships with acceptance criteria and required evidence. Reviewer reviews the plan before implementation.
checkpoint: plan-approved

      
Phase 04
Coordinate
PRD HTML and progress HTML become the single source of truth. Both files live in the project unless the user asks for temporary artifacts.

      
Phase 05
Implement in focused step loops
For each step: read PRD + progress, implement only the current step, gather evidence, update progress HTML, compare against criteria. Advance only when criteria are met.
checkpoint: step-N-done

      
Phase 06
Evaluate
If any criterion is unmet, mark the step repairing, repair, update progress HTML, repeat the same step.

      
Phase 07
Repeat / advance · bounded repair
On failure, don't blindly retry. Diagnose, write a better plan, re-attempt. Run at least 15 repair/replan iterations across the whole task before escalating. Escalate earlier only on true blockers.
≥15 replans before escalate

      
Phase 08
Judge
Two gates: plan gate (before implementation) and implementation gate (after the diff). Judge marks each criterion pass/fail/uncertain with evidence. Taste <4 → repair.

      
Phase 09
Repair
Produce a better plan for the failing step — revised approach, smaller sub-step, or new acceptance evidence. Each iteration carries a fresh plan, not a repeat.

      
Phase 10
Report
Definition used, implementation summary, files changed, validation run + result, reviewer findings addressed, residual risks. Write a memory file capturing decisions, non-goals, risks.
checkpoint: complete

    

  







  

    
08

    
Common issues & fixes.


    

      
Symptom
Loop never terminates
No acceptance criteria defined before implementation.
→ Define criteria before starting implementation.

      
Symptom
Same failure repeats
Not replanning, just retrying.
→ Diagnose, write a better plan, try again.

      
Symptom
Subagent ignores directives
Wrong agent selected or directives not passed.
→ Choose agent with matching traits, pass role directives in task.

      
Symptom
Progress HTML not updating
Relying on chat state.
→ Copy subagent outputs into progress HTML explicitly.

      
Symptom
Taste score below 4
Generic / cookie-cutter solution.
→ Trigger repair loop, ask for a more original approach.

      
Symptom
State lost on compaction
No checkpoints recorded.
→ Mirror checkpoints into docs/-handoff.md if native checkpointing unavailable.
